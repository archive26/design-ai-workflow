# 작업 방식 단계

> 상태: **계획** — README의 실습 흐름 6단계를 실제 작업 단위로 나눈 초안이다.
> 각 단계를 진행하면서 실제로 해 본 방식만 `검증됨`으로 바꾸고, 맞지 않는 부분은 고친다.

## 상태 표시

README 정리 원칙("계획, 실험 중인 내용, 실제로 검증한 내용을 구분한다")에 맞춰 모든 문서 맨 위에 상태를 적는다.

| 상태 | 뜻 |
|---|---|
| 계획 | 아직 해 보지 않은 방식이나 기준 |
| 실험 중 | 한 번 이상 적용했지만 결과를 검토하는 중 |
| 검증됨 | 실제 업무에 적용해서 쓸모를 확인함 |

## 폴더 구성

"관리할 자료" 표의 분류를 그대로 폴더로 둔다. 필요해질 때 만들고, 빈 폴더를 미리 만들지 않는다.

```
skills/      공통 Skill (여러 프로젝트에서 재사용)       ← work-log 있음
agents/      공통 Subagent 설정
prompts/     재사용 프롬프트
guides/      진행 순서·사용 가이드                     ← 이 문서
projects/    프로젝트별 적용 기록 (예: projects/ad-01/)
reports/     적용 결과·한계·개선 보고서
```

- **공통 지침**(skills, agents, prompts, guides)과 **프로젝트별 기록**(projects)을 나눈다.
- 회사 자료는 개인 저장소에 넣어도 되는 범위인지 먼저 확인한다. 안 되는 자료는 요약이나 익명화한 형태로만 남기거나 저장소 밖에 둔다.

## 1단계. 업무 목적과 기존 피드백 정리

**목표:** 기존 광고 이미지 피드백을 앞으로 쓸 기준의 재료로 모은다.

할 일
1. 이번 실습의 업무 목적을 한 문단으로 적는다. (어떤 광고 소재를, 누구를 위해, 무엇을 나아지게 하려는지)
2. 기존 광고 이미지와 받은 피드백을 모은다. 원문은 가능한 한 그대로 둔다.
3. 피드백을 **기획 / 제작 / 검토** 세 단계로 분류한다.
4. 반복해서 나온 피드백과 한 번만 나온 피드백을 구분한다.

산출물
- `projects/<프로젝트명>/brief.md` — 업무 목적
- `projects/<프로젝트명>/feedback.md` — 피드백 원문과 분류표

완료 기준
- 피드백마다 "어느 단계에서 지킬 기준인가"가 표시되어 있다.

디자이너가 판단할 것
- 어떤 피드백을 기준으로 삼고, 어떤 것을 일회성 의견으로 둘지 정한다.

## 2단계. Skill·Subagent 개념 및 활용 사례 조사

**목표:** 1단계에서 정리한 일 중 무엇을 Skill로, 무엇을 Subagent로 만들지 판단할 근거를 얻는다.

할 일
1. Claude Code 공식 문서에서 Skill과 Subagent의 구조, 불러오는 방식, 차이를 정리한다.
2. 디자인 업무와 비슷한 활용 사례를 2~3개 찾는다.
3. 1단계의 업무를 아래 기준으로 나눈다.

| 구분 | 어울리는 일 |
|---|---|
| Skill | 매번 같은 절차·형식·판단 기준으로 하는 일 (예: 작업 기록, 검토 체크리스트) |
| Subagent | 따로 맡겨서 결과만 받으면 되는 조사·분석·검토 (예: 레퍼런스 조사, 기준 대비 검토) |
| 직접 함 | 목적·방향 설정, 최종 판단 |

산출물
- `guides/skill-subagent-basics.md` — 개념 정리와 참고 사례 (출처 링크 포함)
- `projects/<프로젝트명>/plan.md` — 만들 Skill·Subagent 후보 목록

완료 기준
- 후보마다 "왜 Skill(또는 Subagent)인가"가 한 줄씩 적혀 있다.

---

## 3단계. 필요한 개인 Skill·Subagent 구축

**목표:** 2단계 후보 중 **가장 필요한 것부터 최소 구성**으로 만든다.

할 일
1. 후보 중 첫 적용에 꼭 필요한 것만 고른다. (권장: Skill 1~2개, Subagent 1~2개)
2. Skill은 `skills/<이름>/SKILL.md`, Subagent는 `agents/<이름>.md`로 작성한다.
   - 1단계에서 정한 기준을 그대로 옮겨 쓴다. 새 기준을 지어내지 않는다.
   - 출력 형식을 정해 둔다 (결과를 비교·검토하기 쉽게).
3. Claude Code가 읽을 수 있게 설치한다.
   - Skill: `~/.claude/skills/` 또는 `.claude/skills/`에 복사하거나 링크
   - Subagent: `~/.claude/agents/` 또는 `.claude/agents/`에 복사하거나 링크
4. 작은 예시 하나로 시험해 보고, 결과를 보고 한 번 고친다.

후보 예시 (계획)
- Skill `ad-brief` — 새 광고 소재 기획 시 기준 체크와 브리프 형식
- Skill `ad-review` — 완성안을 피드백 기준으로 검토하는 체크리스트와 출력 형식
- Subagent `reference-researcher` — 레퍼런스 조사와 요약
- Subagent `design-reviewer` — 기준표에 따라 시안을 검토하고 근거와 함께 보고

산출물
- `skills/`, `agents/` 아래 파일, 각 파일 맨 위에 상태 `실험 중`

완료 기준
- 예시 입력 하나로 원하는 형식의 결과가 나온다.

---

## 4단계. 실제 디자인 기획·제작·검토에 적용

**목표:** 새 광고 소재 하나를 **기획부터** Skill·Subagent와 함께 진행한다.

| 단계 | 사용 | 디자이너 역할 |
|---|---|---|
| 기획 | `ad-brief` Skill, `reference-researcher` Subagent | 목적·방향 확정, 조사 결과 채택 여부 판단 |
| 제작 | 기획 단계 기준을 참고하며 직접 제작 (Figma) | 시안 제작 |
| 검토 | `ad-review` Skill, `design-reviewer` Subagent | 검토 근거 확인, 수정 여부 최종 판단 |

할 일
1. 각 단계에서 AI에게 준 지시와 받은 결과를 기록한다.
2. AI 결과를 그대로 쓴 것 / 고쳐 쓴 것 / 버린 것을 표시한다.
3. 매일 `work-log` Skill로 그날 한 일을 Figma에 짧게 남긴다.

산출물
- `projects/<프로젝트명>/log.md` — 단계별 지시·결과·판단 기록
- Figma 작업 기록 프레임 (`MM/DD 작업 기록`)

완료 기준
- 광고 소재 하나가 기획·제작·검토를 모두 거쳤다.

---

## 5단계. 적용 결과와 한계 확인

**목표:** 4단계 기록을 보고 무엇이 실제로 도움이 됐는지 확인한다.

확인할 것
- 시간: 전보다 줄었거나 늘어난 작업
- 품질: 기존 피드백이 다시 나왔는지, 새 기준으로 미리 걸러졌는지
- 정확도: Subagent 검토 결과 중 맞은 것과 틀린 것
- 한계: AI가 판단하기 어려웠던 부분, 지시를 여러 번 고쳐야 했던 부분

산출물
- `projects/<프로젝트명>/review.md` — 잘 된 점 / 한계 / 원인 추정

완료 기준
- 각 Skill·Subagent마다 "계속 쓸지, 고칠지, 뺄지"가 정해져 있다.

---

## 6단계. 지침 보완 및 결과 보고서 작성

**목표:** 검증된 내용을 공통 지침에 반영하고, 실습 결과를 보고서로 남긴다.

할 일
1. 5단계 결과에 따라 Skill·Subagent를 고친다. 쓸모가 확인된 것은 상태를 `검증됨`으로 바꾼다.
2. 여러 번 다시 쓴 지시문은 `prompts/`로 옮긴다.
3. 이 문서(작업 방식 단계)도 실제로 한 방식에 맞게 고친다.
4. 결과 보고서를 쓴다.

보고서 구성
- 목적과 범위
- 만든 Skill·Subagent와 역할
- 적용 과정 (4단계 기록 요약, Figma 작업 기록 참고)
- 결과와 한계
- 다음 실습에서 바꿀 점

산출물
- `reports/<YYYY-MM>-<주제>.md`

완료 기준
- 다음 프로젝트에서 그대로 가져다 쓸 수 있는 공통 지침과, 이번 프로젝트에만 해당하는 기록이 나뉘어 있다.

---

## 모든 단계에 공통으로 하는 일

- **매일:** `work-log` Skill로 그날 실제로 한 일만 Figma에 기록한다.
- **단계를 마칠 때:** 산출물 상태(계획 / 실험 중 / 검증됨)를 갱신하고 커밋한다.
- **보안:** 비밀번호, API 키, 토큰은 어떤 파일에도 적지 않는다.
